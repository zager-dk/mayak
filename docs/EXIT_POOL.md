# VLESS exit pool (NODE-API-01)

The managed VLESS/Reality pool is **disabled by default**. Set `MAYAK_VlessPool__Enabled=true` only after the agent follow-up is installed and exits have protocol-specific reports. This API change alone does not make an exit ready or prove public connectivity.

Administrators configure an endpoint with `POST /api/admin/exit-endpoints` and update it with `PATCH /api/admin/exit-endpoints/{id}`. Requests use the existing Admin role. Public endpoint values include host, port, Reality public key, SNI, short ID, fingerprint, flow, and TCP or XHTTP transport settings; private keys are not accepted or exposed. Changing any public identity value increments `identityVersion` and clears readiness. Capacity is a positive `capacitySlots` count and cannot be lowered beneath occupied slots. Slots are conservatively retained; this API has no unsafe release path.

Readiness is accepted only on the authenticated server's `POST /agent/v1/report` with `protocol=vless`. The API stamps receipt time and requires a matching identity version, the exact requested credentials revision, runtime/config/self-test success, `dryRun=false`, no error, and report age at most 120 seconds. Stale or future credentials revisions cannot pre-authorize another desired state. Legacy reports and hello/poll messages do not establish VLESS readiness. Agent report fields: `Protocol`, `IdentityVersion`, `CredentialsRevision`, `RuntimeReady`, `ConfigValid`, and `SelfTestPassed`.

The API persists an internal SHA-256 fingerprint of each endpoint's effective credential membership (assigned device IDs, stable Xray IDs and device Enabled state, filtered by current account Enabled/PaidUntil). It reconciles that fingerprint under the existing PostgreSQL device advisory transaction lock before state, reports and readiness-dependent delivery, and before/after access mutations. A changed fingerprint increments the endpoint desired revision and clears readiness; identical polls/reports/retries do neither. Natural expiry is reconciled on the next observation, not by a background timer. Reconciliation before renewal also catches an expiry that occurred without an intervening agent poll, so an old active-membership ACK cannot silently authorize the renewed state. Account changes invalidate only endpoints whose effective list changed; all affected endpoint users wait for a fresh exact ACK. Occupied slots are never released by this process, even after removal ACK: capacity release remains a separate future workflow.

The additive `PoolCredentialsSnapshot` migration leaves legacy keys, IPs, cluster identity and assignments intact. Empty endpoints retain bootstrap revision 0. A populated existing pool conservatively gains a new desired revision on its first reconciliation and needs a fresh ACK; no stored legacy AWG device is converted. This internal fingerprint is not a new agent protocol field.

Existing `GET /api/app-key` and gateway config requests remain AWG. A new root uses `GET /api/app-key?protocol=vless`; the app-key must already be enabled. Managed devices opt in at creation with `protocol=vless` and a stable `installationId`; a repeated create with that id returns the same device. VLESS devices are excluded from legacy AWG desired-state accounts and appear in `AgentState.PoolDevices` only on their assigned exit, with stable `XrayId`, endpoint public identity, and `CredentialsRevision`. Agent follow-up must apply/reconcile these credentials and report protocol ACK before configuration delivery. Before an exit is ready, responses are retryable `no_ready_exit` or `provisioning`.

Gateway and `/sub` use the same stored endpoint assignment. A pool subscription is issued only for an explicitly opted-in pool device and only while its assignment is ready. Existing AWG devices and subscriptions do not change protocol when the feature flag changes. `XrayId` stays stable across retries. The API does not promise failover time, internet reachability, or the existing 35 Mbps AWG rate for VLESS.

Managed `POST /api/devices` retries find the current account's existing `installationId` inside the shared lock before checking MaxDevices. At the limit, the same installation returns the same pending/ready device; a different installation is still rejected. Pending pool creation or owner/admin file export returns retryable `503 no_ready_exit` or `503 provisioning`, without any legacy AWG key/config. Disabled managed accounts/devices are denied. Ready managed file exports contain a selected-endpoint Xray-only `vpnKey`, native Xray JSON in `conf` with a `.json` filename, and its VLESS link; legacy devices keep their existing AWG files. Pool gateway requests cannot switch an existing pool installation to AWG.

Pool gateway containers follow the existing native `ApiV2ServerConfig`/`ContainerConfig` format: `container=amnezia-xray`, protocol object `xray`, and `last_config` containing serialized native Xray JSON. TCP maps to the existing Core helper's `raw` transport to preserve Vision flow; XHTTP keeps its selected host/path/mode and omits TCP flow. Host/Reality public identity and device UUID come only from the assigned endpoint/device. The integration fixture under `work/review-node-integration` compiles the existing read-only native model sources and consumes real HTTP-emitted gateway and file configurations for both transports; this validates parsing/serialization, not VPN connectivity.

Agent follow-up: every authenticated exit with a configured pool receives `AgentState.PoolEndpoint`, including when `PoolDevices` is empty. It carries `EndpointId`, public identity, `IdentityVersion`, `DesiredCredentialsRevision`, and allow/capacity settings. The agent must base its VLESS ACK on this delivered endpoint state, then consume `PoolDevices` and apply each listed `XrayId`/revision. Report readiness only after actual runtime, configuration, and self-test checks, echoing the endpoint identity version and applied credentials revision. The API does not claim those agent changes or a production pilot are present.
